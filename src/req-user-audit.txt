GOAL
----
Find every endpoint / service / function that is already protected by
verifyToken() (so the authenticated identity is available at req.user)
but STILL asks the client to supply the authenticated user's own
identifier (accountId / userId / id / owner / senderId / actorId ...)
through body, params, query, DTO or validation schema.


##############################################################
#  BACKGROUND FACTS ESTABLISHED DURING THE TRACE             #
##############################################################

1. AUTH MIDDLEWARE
   File: src/middlewares/verifyToken.ts
   verifyToken() decodes the JWT and assigns:

       const userPayload: UserPayload = {
         id: decoded.id,
         email: decoded.email,
         roles: []
       }
       req.user = userPayload

   => req.user.id IS the authenticated Accounts.id (primary key of the
      accounts table). Confirmed via src/utils/jwt.util.ts where the
      token payload is built from { id, email, roles }.

   This means: for EVERY route below that carries verifyToken(), the
   authenticated accountId is already available server-side and does
   not need to come from the client.

2. TWO ENDPOINTS ALREADY DO IT CORRECTLY (reference implementations)

   - src/modules/post/controller.ts -> create()
         accountId: req.user.id
   - src/modules/message/controller.ts -> createMessage()
         senderId: req.user.id

   These prove the pattern is intended in this codebase; the findings
   below are inconsistencies with the project's own convention.

3. verifyRole() IS EFFECTIVELY A NO-OP  (affects confidence ratings)
   File: src/middlewares/verifyRole.ts

       const hasPermission = requiedRoles.some((role) => role)

   This maps over the REQUIRED roles, not the user's roles, and returns
   true whenever the required-roles array is non-empty. Additionally
   verifyToken() always sets roles: [] (empty), so no real role data is
   ever present in req.user.

   CONSEQUENCE: routes that "look" admin-protected (groups/*,
   advertisements/*, reports PUT) are in practice reachable by ANY
   authenticated user. They were therefore NOT auto-excluded as "admin
   endpoints"; they are reported at MEDIUM confidence with this caveat
   stated explicitly.

4. Only genuinely admin-intent operations were excluded per the brief:
   POST /v1/accounts/ban/:id, POST /v1/accounts/unban/:id,
   PUT /v1/accounts/ (setRolesToAccount), PUT /v1/reports/:targetId.
   Public routes (auth, email, all unauthenticated GETs, profile
   create/setToAccount) were excluded as instructed.

5. Socket.IO layer (src/middlewares/socketio.ts) was checked and is
   CORRECT - it derives socket.data.userId from the verified token and
   never trusts a client-supplied id. No findings there.

Function:
update()

Route:
PUT /v1/posts/:postId

Authentication:
verifyToken ✅

Current code:

const data = req.body;
const dto = new UpdatePostInputDTO({
  postId: Number(postId),
  owner: Number(data.owner),
  ...
});

Problem:

Authenticated user already exists in req.user but `owner` is still
requested from the request body. This is the identifier the service
uses as the ownership proof:

  PostServiceImpl.update() line 55:
    if (post.accounts.id !== Number(data.owner))
      throw new Forbidden('You are not the owner of this post')

Because `owner` is client-controlled, the ownership check compares two
client-influenced values instead of comparing the post owner against
the authenticated user. Any authenticated user can edit any post by
sending the victim's accountId as `owner`.

Recommendation:

Use:

const owner = req.user.id;

instead of accepting `owner` from the request body, and drop `owner`
from UpdatePostInputDTO's client-facing surface.

Call chain:

Router (src/routes/v1/post.route.ts)
→ verifyToken()
→ PostController.update()
→ PostServiceImpl.update()
→ PostRepoImpl.getOne() / PostRepoImpl.update()
→ PostMediaRepositoriesImpl.deleteNotIn() / create()

bound to the authenticated user rather than fully client-controlled.
